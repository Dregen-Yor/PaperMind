# PaperMind 轻量语义树索引实验：方案与施工手册

> 日期：2026-09-15  
> 分支：`exp/tree`  
> 状态：第一版方案已确认，尚未进入代码实现

## 1. 背景与问题

PaperMind 当前的论文索引位于 `src/utils/pageIndex.ts`。它先按章节边界或固定页数生成叶节点，由 LLM 为每个叶节点生成标题和摘要，再生成一个根摘要。检索时并不会沿根节点逐层搜索，而是把所有叶节点摊平，让 LLM 一次性评分并选取 Top-K。

现有方案具备可用的端到端问答流程，但存在两个核心问题：

1. 当前结构主要受到章节边界和固定页数影响，不是 LLM 根据论文内容形成的整体理解。
2. 完整 QASPER 结果中，PaperMind 平均只有约 1.65 个叶节点，结构过粗，实际上没有形成足够的可导航空间。

本实验希望验证：**能否让 LLM 从全文语义和论证关系出发，一次性构造一棵小型论文语义树，并在不增加查询阶段 LLM 串行调用次数的前提下，改善证据检索。**

## 2. 第一版冻结目标

第一版只实现和验证以下目标：

- 每篇论文生成一棵由 LLM 自主理解形成的粗粒度语义树。
- 树的组织依据只能是概念、主张、组成、解释、支持、比较和限制等语义关系，不能以论文目录或章节边界作为父子关系依据。
- 树保持很小：根节点之外最多两层，总节点数不超过 16 个。
- 一篇普通论文最多使用一次 LLM 调用完成初始语义树构建。
- 树只承担导航职责；完整、准确、可引用的原始信息保存在独立的原文证据块中。
- 语义树在后台构建，不能阻塞论文导入、阅读或首次提问。
- 树未完成、超时、失败或输出不合法时，继续使用现有检索路径，不影响产品可用性。
- 查询阶段不因树的层级增加额外串行 LLM 调用；整棵小树在现有的一次检索判断中使用。

## 3. 第一版明确不做的内容

为了先验证方向和速度，以下内容不进入第一版：

- 不为每个文本块分别调用 LLM 生成详细理解卡。
- 不逐层调用 LLM 进行多轮 agentic tree search。
- 不在建树时生成大规模 claim、问题集、实体关系或知识图谱。
- 不实现所有节点之间的两两关系推理。
- 不把论文目录转换成树，也不把 `Introduction / Method / Results` 等章节名直接作为语义节点。
- 不为超长论文设计多轮递归建树；第一轮实验先覆盖能够在一次模型上下文中容纳的普通论文。
- 不在第一版实现基于用户历史的树增量生长。该方向保留为后续阶段，在初始语义树证明有效后再讨论。

## 4. 核心架构：证据存储与语义导航分离

第一版必须把“原始信息保存”和“语义结构生成”设计成两个独立层次：

```text
轻量语义树
  只保存论文的概念结构、语义关系和证据引用
                         │
                         ▼
原文证据块存储
  保存完整文本、页码、顺序、位置和相邻上下文
```

语义树中的标题和描述都是 LLM 生成的导航元数据，不能作为最终答案的事实依据。回答问题时，必须根据节点中的引用回到原文证据块，最终上下文和来源均来自原文。

这一分离保证：

- 树可以保持足够小，适合快速构建和快速查询。
- LLM 摘要即使存在偏差，也不会替代原文成为证据。
- 后续可以修改、重建或增量细化树，而无需改变原始论文数据。
- 引用始终能够回溯到具体页码和原文位置。

## 5. 原文证据块

### 5.1 定义

原文证据块是最小可引用单位，但不是语义树节点。它只负责稳定保存论文原始信息，并为语义树提供可引用的锚点。

建议第一版按约 400–800 token 形成一个块，优先在自然段落边界停止。块的大小用于控制后续上下文预算，不决定语义树的父子结构。

### 5.2 必备信息

每个证据块至少保留：

| 字段 | 含义 |
|---|---|
| `id` | 论文内稳定且唯一的块 ID，例如 `B001` |
| `rawText` | PDF 解析得到的原始文本，供校验和引用 |
| `normalizedText` | 仅用于搜索的轻度清洗文本 |
| `startPage` / `endPage` | 原始页码范围，包含端点 |
| `order` | 在论文中的原始顺序 |
| `previousId` / `nextId` | 相邻证据块，用于取回上下文 |
| `sourceType` | 正文、图注、表注、公式附近文本、脚注或其他 |

如果 PDF 解析能力允许，后续可增加页内坐标或字符偏移；第一版不以此作为必要条件。

### 5.3 原文正确性原则

- `rawText` 一经生成不得被 LLM 改写。
- 页眉、页脚、断词和换行等修正只进入 `normalizedText`，不能覆盖原始文本。
- 语义树只能引用真实存在的证据块 ID。
- 最终回答上下文必须重新从证据块读取，不能直接使用树节点描述代替。
- 即使某个证据块没有被语义树引用，也必须继续保留在原文存储中，并可由现有平面检索召回。

## 6. 轻量语义树

### 6.1 树表达什么

树表达的是 LLM 对整篇论文的整体理解和论证架构，例如：

```text
论文的中心问题或核心结论
├─ 某个关键困难为何无法由已有方法解决
├─ 作者提出的核心解决机制
│  ├─ 关键设计及其作用
│  └─ 设计成立所依赖的假设
├─ 支撑该机制的证据链
│  ├─ 主实验结果
│  ├─ 消融证据
│  └─ 机制分析
└─ 结论成立的条件与边界
```

该结构只是示意，不是固定模板。理论论文、方法论文、系统论文和实证研究应由 LLM 根据各自内容形成不同结构。

### 6.2 规模限制

第一版采用以下硬限制：

- 一个根节点；
- 根节点下 3–5 个一级语义模块；
- 所有一级模块合计包含 6–10 个二级证据簇；
- 根节点之外最多两层；
- 整棵树最多 16 个节点；
- 每个节点的描述限制为 1–2 句话；
- 总输出建议控制在约 600–1000 token。

节点不足时不需要为了满足数量而虚构分支。内容简单的论文可以只生成一层；内容复杂也不得在第一版突破规模限制。

### 6.3 最小节点信息

每个节点只保存以下导航信息：

| 字段 | 含义 |
|---|---|
| `id` | 树内稳定、唯一的节点 ID |
| `label` | 论文特有的概念、主张或证据簇名称 |
| `description` | 该节点在整篇论文中承担的作用 |
| `relationToParent` | 它与父节点之间的语义关系 |
| `evidenceRefs` | 与该节点相关的原文证据块 ID |
| `children` | 子节点 |

`label` 应使用论文特有语义，例如“跨层表示对齐机制”，而不是泛化的“方法”“实验”或“第三节”。

### 6.4 语义关系

父子边必须明确表达语义关系。第一版支持以下常见关系，并允许在确有必要时输出简短的其他关系：

| 关系 | 含义 |
|---|---|
| `motivates` | 子节点说明为什么需要父节点所表达的主张或设计 |
| `constitutes` | 子节点是父节点方法、机制或概念的组成部分 |
| `supports` | 子节点为父节点结论提供证据 |
| `explains` | 子节点解释父节点现象或机制 |
| `compares` | 子节点通过比较刻画父节点结论 |
| `limits` | 子节点限定父节点的成立条件或适用范围 |
| `contradicts` | 子节点提供相反、不一致或失败证据 |

显式关系的目的不是预先规定树的内容，而是迫使模型说明“为什么这个节点属于这里”，避免父子关系退化为目录包含关系。

### 6.5 多重归属

第一版保持节点本身为单父节点树结构，但允许同一个 `evidenceRef` 被多个语义节点引用。

例如，一个消融实验块既可以支撑“模块 A 的有效性”，也可以限制“整体提升来自所有组件”的主张。通过共享证据引用表达跨主题联系，第一版暂不升级为完整图结构。

## 7. 只按语义构造的约束

### 7.1 输入约束

- 建树输入是带稳定 ID 和页码信息的原文证据块。
- 不向模型提供预先解析的目录树或章节父子关系。
- 保留原文自然顺序，便于模型理解上下文；顺序本身不得成为分组依据。
- 章节标题可能作为原文内容自然出现，但提示必须明确：不得依照章节标题或页码连续性构造父子结构。

### 7.2 输出约束

- 禁止直接以 `Introduction / Related Work / Method / Experiments / Results / Conclusion` 等章节名作为节点名称。
- 节点必须描述论文特有的概念、主张、机制、证据簇或限制。
- 每条父子边必须填写 `relationToParent`。
- 语义相关但分散在不同页、不同章节的证据可以进入同一节点。
- 一个证据块可以被多个节点引用。
- 模型不得输出不存在的证据块 ID，也不得改写 ID 指向的原文。
- 无法确认的关系应保持粗粒度，不能为了形成漂亮的树而虚构论证。

### 7.3 语义树与目录重合的判断

语义树与论文目录局部重合不必然是错误；有些论文的写作结构本身就符合论证结构。判断标准不是页码是否连续，而是：

- 节点是否表达论文特有的语义，而不是章节功能；
- 父子关系能否用明确的语义关系解释；
- 是否能够把跨章节、但共同支撑一个概念或主张的证据组织到一起；
- 是否避免仅凭标题或原文位置归组。

## 8. 初始建树流程

第一版的建树流程固定为：

```text
PDF 原文
  → 本地解析并生成证据块
  → 将全文证据块一次性提供给索引 LLM
  → LLM 输出不超过 16 个节点的语义树
  → 本地校验结构和证据引用
  → 校验通过后持久化；否则继续使用现有索引
```

### 8.1 单次调用原则

- 每篇论文最多一次初始建树 LLM 调用。
- 不逐块摘要，不逐节点生成，不递归调用模型。
- 一次调用同时完成全局理解、语义分组、关系组织和证据引用。
- 树的输出必须是结构化数据，避免依赖自然语言格式解析。

### 8.2 后台执行与降级

- 论文导入和原文切块完成后即可进入现有可用状态。
- 语义树构建在后台进行，UI 不等待建树完成。
- 建树未完成时，问答继续使用现有检索路径。
- LLM 请求失败、超时、返回非法结构或引用不存在的块时，不写入不完整语义树。
- 失败不能阻止论文阅读、普通检索和问答。
- 后台任务应可取消，应用退出不需要等待其完成。

### 8.3 本地校验

LLM 输出至少通过以下校验才能成为可用索引：

- JSON 或目标结构能够完整解析；
- 节点总数、层数和每层规模符合限制；
- 节点 ID 唯一；
- 除根节点外，每个节点恰有一个父节点；
- 没有环和孤立节点；
- 所有 `evidenceRefs` 都指向真实证据块；
- 所有关系字段合法且非空；
- 节点名称和描述非空；
- 不存在明显以通用章节名代替语义节点的情况。

证据块覆盖率作为诊断指标记录，不作为第一版的硬失败条件。没有进入树的内容仍可通过平面检索访问。

## 9. 查询与取证流程

第一版不实现逐层多轮搜索，而是在一次检索判断中使用完整小树：

```text
用户问题
  → 将完整轻量树作为论文地图提供给检索判断
  → 一次返回一个或多个相关语义节点
  → 汇总节点引用的证据块
  → 必要时结合现有平面检索候选和相邻块
  → 在统一上下文预算内读取原文
  → 使用原文生成回答和来源
```

关键约束：

- 查询阶段不能因为树有两层而增加两次或多次 LLM 调用。
- 多分支问题允许一次选中多个节点。
- 树节点描述只帮助路由，不能直接进入最终事实回答，除非同时取回其引用原文。
- 若选中节点没有有效证据、证据不足或树不可用，必须回落到现有平面检索。
- 最终来源仍使用原文页码，而不是语义节点 ID。
- 合并证据时继续服从统一的上下文预算，不能因为节点引用较多而无限扩张。

## 10. 性能预算与产品约束

### 10.1 用户可感知路径

- 论文导入后不等待语义树即可阅读和提问。
- 语义树构建耗时不计入首次可用时间。
- 查询阶段维持现有 LLM 调用数量，不增加额外串行规划调用。
- 树解析、节点映射和证据块读取属于本地开销，目标是相对现有检索不产生明显可感知延迟。

### 10.2 建树成本

- 普通论文只允许一次建树模型调用。
- 输出规模限制在约 600–1000 token。
- 输入优先使用完整原文证据块，避免预摘要导致信息丢失和额外调用。
- 第一次实验只评测能够被一次模型上下文容纳的论文。
- 必须单独记录输入 token、输出 token、建树时延、失败率和模型信息。

### 10.3 缓存与复用

- 建好的树按论文持久化，不能在每次提问时重建。
- 树需要记录 schema 版本、构建模型、构建配置和提示版本，以便将来判断是否需要重建。
- 同一论文内容未变化时复用已有树。

## 11. 评测方案

### 11.1 现有参照结果

仓库现有完整 QASPER 结果可作为方向参照：

| 方法 | Evidence Recall | Hit Rate | Context Precision | MRR | Answer F1 |
|---|---:|---:|---:|---:|---:|
| PaperMind 当前 LLM 索引 | 0.838 | 0.861 | 0.187 | 0.798 | 0.194 |
| BM25 | 0.852 | 0.902 | 0.221 | 0.602 | 0.208 |
| BGE-M3 cosine | 0.900 | 0.959 | 0.238 | 0.780 | 0.209 |
| Hybrid rerank | 0.891 | 0.934 | 0.252 | 0.759 | 0.155 |

这些结果来自不同时间和部分不同回答模型，Answer F1 与端到端时延不能直接作为严格横向结论。正式实验必须重新在相同条件下运行。

### 11.2 严格对照

第一轮正式实验至少比较：

1. 当前 PaperMind 扁平 LLM 索引；
2. 新的轻量语义树索引；
3. BM25；
4. BGE-M3 cosine；
5. 已有 hybrid-rerank 强基线。

所有方法必须使用：

- 同一份 QASPER 样本；
- 同一份原文表示和 evidence mapping；
- 同一个最终回答模型；
- 同一个上下文预算；
- 相同的回答提示和拒答规则；
- 相同的缓存口径和错误统计方式。

### 11.3 核心检索指标

- `evidenceRecall`
- `evidenceHitRate`
- `contextPrecision`
- `mrr`
- `contextTokens`
- `answerF1`
- `unanswerableAccuracy`

### 11.4 新增树诊断指标

- 每篇论文节点总数；
- 实际树深；
- 一级和二级节点数量；
- 被树引用的证据块覆盖率；
- 一个证据块被多个节点引用的比例；
- 引用跨越原始章节或非连续页区间的节点比例；
- 建树 LLM 调用数；
- 建树输入、输出 token；
- 建树 P50 / P95；
- 建树失败率和降级率；
- 每个问题选择的节点数；
- 选中节点是否覆盖 gold evidence；
- 节点引用扩张后的上下文 token 数；
- 查询阶段 LLM 调用数是否相对当前方案增加。

### 11.5 第一版成功标准

第一版先验证方向，不预设必须超过所有强基线。至少满足以下条件才值得进入增量演化阶段：

- 能稳定产生符合大小和结构约束的语义树；
- 人工抽查确认树主要按照论文特有语义和论证关系组织，而不是改写目录；
- 不降低论文导入后的首次可用速度；
- 查询阶段不增加额外串行 LLM 调用；
- 建树失败时能够完整降级，不影响问答；
- 在相同评测口径下，至少有一项主要检索指标相对当前 PaperMind 明显改善，且其他主要指标没有不可接受的退化；
- 树选中的证据最终能够准确回溯到原文和页码。

## 12. 施工顺序

以下步骤是后续实现时的推荐顺序。本轮只冻结方案，不执行代码修改。

### 阶段 A：证据块与数据契约

1. 定义原文证据块的数据结构和稳定 ID 规则。
2. 明确 `rawText` 与 `normalizedText` 的生成和保存边界。
3. 验证分页、相邻关系及图表说明等来源信息不丢失。
4. 为语义节点和语义树定义带版本的数据结构。
5. 增加结构、引用和规模校验规则。

完成标志：不调用 LLM 也能稳定生成并校验原文证据块；任意引用都能回到原始页码和文本。

### 阶段 B：单次 LLM 语义建树

1. 设计全文证据块输入格式。
2. 设计只按语义组织的建树提示和结构化输出约束。
3. 强制节点数、深度、描述长度和语义关系限制。
4. 对输出执行本地校验，非法结果不得持久化。
5. 保存模型、提示版本、token 和时延信息。

完成标志：普通论文最多一次模型调用即可得到不超过 16 个节点的合法语义树。

### 阶段 C：后台任务与产品降级

1. 将语义树构建从导入可用路径中分离。
2. 保证阅读和问答不等待语义树。
3. 实现失败、超时、取消和应用退出时的安全处理。
4. 树未就绪时继续使用现有索引。
5. 论文内容和树版本未变化时复用已有结果。

完成标志：关闭语义树、建树失败和建树进行中三种状态下，现有功能均保持可用。

### 阶段 D：单轮树路由与原文取证

1. 将整棵小树加入现有检索判断，而不是逐层调用。
2. 支持一次选取一个或多个相关节点。
3. 根据节点引用取回原文证据块，并处理相邻上下文。
4. 在统一预算内与现有平面候选合并或降级。
5. 最终回答继续引用原始页码。

完成标志：树检索不会增加查询阶段串行 LLM 调用，且所有回答上下文均来自原文证据块。

### 阶段 E：Benchmark 与人工检查

1. 在现有 `bench/` 契约内增加轻量语义树实验模式。
2. 增加树结构、覆盖率、成本和降级诊断指标。
3. 使用固定模型和上下文预算重新运行对照组。
4. 对代表性论文进行人工结构检查，确认不是目录复刻。
5. 根据证据指标、速度和失败率决定是否继续投入。

完成标志：能够用同一套结果文件同时回答“检索是否变好”“树是否真是语义结构”“产品是否仍然足够快”。

## 13. 风险与处理原则

| 风险 | 第一版处理原则 |
|---|---|
| LLM 复制论文目录 | 禁止通用章节名；要求论文特有节点及显式语义关系；人工抽查 |
| LLM 引用不存在的块 | 本地严格校验，整棵树降级，不猜测修复 |
| 节点描述产生事实偏差 | 描述只用于导航；回答必须重新读取原文 |
| 树过大导致输入和检索变慢 | 两层、16 节点和短描述硬限制 |
| 一次全文输入超过上下文 | 第一轮不做递归补救，记录为不支持或降级现有检索 |
| 树没有覆盖某些内容 | 原文块始终保留，平面检索继续作为安全网 |
| 多主题证据无法放进单父树 | 允许同一证据块被多个节点引用 |
| 建树延迟影响导入 | 全程后台执行，不作为论文可用前置条件 |
| 树检索增加热路径调用 | 整棵小树一次选择，禁止逐层串行调用 |

## 14. 后续但未冻结的方向

只有第一版证明语义树在速度和检索质量上有效后，才讨论以下方向：

- 根据用户真实提问、连续追问、高亮和来源点击，增量细化高关注分支；
- 将单父树扩展为显式语义图；
- 对超长论文做分阶段或分层建树；
- 对局部节点按需生成更详细的主张、条件、反例和问题入口；
- 让检索模型在证据不足时提出跨分支补证计划；
- 在 UI 中展示可解释的论文地图和取证路径。

这些方向不是第一版的验收条件，也不能在实现第一版时提前扩大范围。

## 15. 第一版最终定义

> PaperMind 第一版语义树索引是一棵不超过 16 个节点、最多两层、由单次 LLM 全文理解生成的小型论文导航结构。它仅按照论文特有的概念、主张及论证关系组织，不以目录或章节边界为父子依据。树节点只保存简短语义描述和原文证据块引用；完整、准确的信息始终保存在独立的原文证据块中。建树在后台执行且可失败降级，查询时整棵树在现有的一次检索判断中使用，不增加额外串行 LLM 调用。
