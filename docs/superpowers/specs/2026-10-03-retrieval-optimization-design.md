# 检索热路径与目录先验优化

状态：用户于 2026-10-03 确认方案 A，按下述范围实施。目录先验保持默认关闭。

## 目标与当前基线

依据 `prompt.md`，在保证首字速度的前提下改善原文证据召回。当前基线来自远程
`8daa5f4`，已经实现段落 BM25、本地向量、结构卡片三路融合，查询前零 LLM 路由。
因此不再重复实现卡片方案，也不使用提示词中的历史数字宣称新算法的实际收益。

继续保持产品与 benchmark 共用 `src/utils` 管线、单轮查询前零 LLM 调用、原文
证据与页码可追溯，以及 benchmark 的 4096 token 预算。回答提示词保持当前版本，
以便将收益归因于检索；产品已有多轮查询改写保持现有触发条件。

## 已确认的重复开销

1. `retrievePassageContext` 每次查询都调用 `buildBm25Scorer`，重新分词全部段落并
   统计词频；卡片词法降级路径也重新构建统计量。
2. `retrieveRagContext` 逐篇检索；同一问题、同一个 embedder 会为每篇拥有向量的
   论文再次执行 `embedQuery`。
3. `fillPassageBudget` 对每个候选重新展开、求和和排序已选段落，以判断 token
   和连续片段数。这些状态可以增量维护。
4. `collectIndexedPapers` 每次发送消息都重新解析索引 JSON 和向量。只在检索层
   按对象缓存会在产品中经常失效，必须同时考虑产品的加载边界。

这些是从当前源码确认的重复计算，尚未测量各项在真实模型上的耗时占比。

## 三种路线

| 路线 | 范围 | 收益与代价 |
| --- | --- | --- |
| A，推荐 | 先消除重复计算，再加入可关闭的目录软先验并做消融 | 速度阶段保持检索结果一致；质量阶段需要同批数据验证，改动集中在现有管线 |
| B | 仅消除重复计算，保留当前三路排序 | 回归风险较小，可以验证结果一致；不主动改善证据排序 |
| C | 增加快速决策模型路由 | 可能改善语义判断，但增加模型加载、推理与失败路径；需先明确 `jev` 身份并证明收益 |

## 推荐设计

### 第一阶段：保持结果一致的速度优化

- 在索引加载后准备段落/卡片 BM25 打分器及段落到卡片、来源标题的映射。缓存
  统计量，不缓存回答或跨请求的查询结果。
- 产品采用有容量限制的已解析索引缓存，按论文 ID 和原始 `indexJson`、
  `pagesJson` 内容验证复用；记录变化、分阶段索引更新和删除后不得使用旧内容。
  只缓存少量最近使用论文，避免长期保留全部向量。benchmark 复用同一索引实例
  的准备结果；序列化格式和 SQLite/IPC 不变。
- 查询向量只在一次 `retrieveRagContext` 调用内复用。同一 embedder、同一查询
  最多一次 `embedQuery`；没有可用段落向量或模型身份不一致时仍不发推理请求。
  失败在本次调用内共用降级结果，下一次提问重新尝试，不缓存失败到后续请求。
- 预算填充增量维护 token 总数和连续片段数：加入一段时，根据左右邻段是否已选
  判断新增、延伸或连接片段。候选顺序、邻段系数、连续跳过上限和最终原文排序
  保持一致；短论文全文进入的行为保持一致。
- 旧平面索引、语义树、用户划选上下文和多轮查询改写继续走现有分支。

第一阶段验收要求包括原文上下文、选中段落、页码、来源、降级模式和 token 预算
一致，不能只比较回答文本或测试执行速度。

### 第二阶段：目录软先验，独立消融

利用现有 `Passage.subsection`，构建轻量目录条目（标题、段落区间）。目录只用于
检索评分，不进入回答事实上下文，也不需要新的 LLM 调用或新的卡片生成请求。

为目录标题建立 BM25 查询打分。标题命中时，所属段落获得一个有独立权重的
RRF 先验；完全无标题命中时跳过该信号。目录不作为硬过滤条件，未命中的章节
仍保留原有 BM25/向量/卡片召回机会，避免目录识别误差直接丢失证据。

新增 `headingWeight` 配置：0 必须与第一阶段结果一致；独立实验配置使用 0.25，
并比较 0、0.25、0.5 三档。配置从 CLI、runner、RAG 依赖到检索层完整传递，
实际值进入结果配置记录；历史默认配置保持原值。

目录权重在真实质量与速度对照完成前默认关闭。仅在同题集、同回答模型和提示词、
同 token 预算下，证据召回与答案质量没有明显下降、检索 P95 未明显恶化时，
再决定是否启用默认值。不得仅凭合成例子或较高 Q 宣称质量提升。

### `jev` 的处理

`prompt.md` 没有给出准确模型名称、仓库或运行方式，目前无法确定它指什么。
本轮 A/B 不依赖该模型；收到准确身份后，单独评估 CPU/WASM 或本地后端支持、
模型体积、热查询耗时和证据判断能力。需要新增推理的路线 C 是独立方案。

## 验证与交付

- 回归测试：准备缓存的失效与容量边界、同问题多篇论文只计算一次查询向量、
  错误降级后下一问恢复、预算连接两个片段时正确扣除分隔符、短文全文进入。
- 结果一致性：比较第一阶段前后的完整检索结果；覆盖卡片缺失、向量缺失、
  模型身份不一致、不同预算和多篇论文。
- 目录用例：问题明确命中某章节时增加该区间的机会；无命中不改变排序；权重
  为 0 完全一致；原文分片和真实页码保持正确；不因标题硬过滤其他证据。
- 本地性能：固定语料、固定问题序列，分别报告准备成本和热查询 P50/P95。
  同一环境先预热再测量，并检查两版结果一致。合成语料只用于工程性能验证。
- 必须运行 `npm test`、`npm run typecheck`、`git diff --check`，并验证应用构建。
- 真实质量：使用冻结的 60 篇/179 题 QASPER 切片，统一回答模型、生成配置和
  4096 token 预算，报告 AnswerF1、EvidenceF1/Recall、检索 P50/P95、TTFT、
  失败率与冷启动成本。仓库当前未提供该切片及已有结果，正式评测需要相应数据
  和模型配置；这项缺失不会被合成数据替代。

实施时先提交第一阶段，再独立提交目录实验；每阶段完成验证后推送。提交中不含
模型权重、PDF、数据库、凭据或生成的应用包。

实施补充（2026-10-04）：已使用仓库公开下载脚本获取 60 篇/179 题切片，保存于

- 索引格式、IPC 和数据库结构无需变更。
